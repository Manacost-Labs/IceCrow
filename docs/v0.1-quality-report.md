# IceCrow v0.1 Quality Gate Report

Date: 2026-08-14
Audited revision: `dfe732b22cbbaeccc7b881200ef1a7f2770ac9d3` plus the Milestones 11–13 working-tree changes described below.

## Verdict

IceCrow v0.1 is **not production-ready**.

The repository has a clean project dependency direction, deterministic and well-covered domain components, a bounded log/replay input model, and a working Windows overlay foundation. Milestone 13 connects accepted `RawLogLine` objects through a non-WPF live coordinator to the same `TrackingSession` used by replay, then coalesces immutable snapshots at the WPF presentation boundary. Synthetic integration tests prove this software path, but production readiness remains blocked on the real Hearthstone acceptance matrix and reconnect evidence.

## Architecture status

### Dependency direction

The project graph is acyclic:

```text
App -> Overlay / Platform.Windows / Hearthstone.Logs / Live / Recording
Live -> Hearthstone.Logs / Hearthstone.Protocol / Tracking
Overlay -> Battlegrounds / Battlegrounds.Memory / Platform.Windows
Recording -> Tracking / Hearthstone.Protocol / Hearthstone.Entities
             / Battlegrounds / Battlegrounds.Memory
Tracking -> Hearthstone.Protocol / Hearthstone.Entities
            / Battlegrounds / Battlegrounds.Memory
Battlegrounds.Memory -> Battlegrounds
Battlegrounds -> Hearthstone.Entities / Hearthstone.Protocol
Hearthstone.Entities -> Hearthstone.Protocol
Hearthstone.Logs / Hearthstone.Protocol / Platform.Windows -> no IceCrow dependencies
```

- No domain project references WPF, `System.Windows`, HWNDs, or UI controls.
- UI code does not parse `Power.log` directly; the App consumes `RawLogLine` objects from the log project.
- Normalized events remain the boundary between parsing and reducers.
- Historical entity, board, opponent, timeline, and replay state is exposed through immutable snapshots or copied read-only collections.
- No core project requires a network or backend service.
- `IceCrow.Live` has no WPF, overlay, App, or Win32 dependency; it consumes the existing bounded log channel directly without adding an unbounded queue.
- Test projects reference only the production project under test and its transitive dependencies.
- `IceCrow.Architecture.Tests` enforces the allowed production dependency graph, rejects cycles, prevents WPF/native window interop in domain modules, and detects test projects coupled to multiple production modules.
- `AGENTS.md` was corrected to document the dependencies already required by deterministic replay composition.

## Performance observations

### Power log input

- Reads incrementally from a byte checkpoint with `FileShare.ReadWrite`; it does not reread the full file after each change.
- Uses file notifications plus a one-second recovery interval rather than a 16 ms polling loop or busy-spin.
- The accepted-line channel is bounded and applies producer backpressure. Worst-case queue retention is now intentionally constrained by a 64 KiB line limit and a maximum of 256 queued items (128 by default).
- Partial lines are bounded, rotation/truncation resets the checkpoint, and missing/access-denied files use recoverable status paths.

### Parser and state reducers

- Generated non-backtracking regular expressions and explicit match checks avoid catastrophic regex backtracking and fragile match assumptions.
- Entity tag mutation is normally O(1); identical values do not emit downstream mutations.
- `TrackingSnapshot` does not include a full entity projection. Full store snapshots are created only for explicit replay/diagnostic materialization and remain budgeted by Recording.
- Combat entry snapshots only the current opponent's in-play minions rather than cloning every tracked entity.
- Battlegrounds lobby state is structurally copied, but the lobby is capped by Hearthstone-scale player counts in replay validation.
- Opponent memory and lobby timelines use immutable array/dictionary replacement. This is appropriate for the small v0.1 lobby but repeated timeline sorting and complete history copying should be benchmarked before adding richer event volume.

### Overlay

- Window geometry is event-driven through WinEventHook. The one-second lifecycle timer is for discovery/liveness recovery, not frame-by-frame geometry polling.
- Modifier state polling is limited to the interactive overlay lifetime and uses a short UI timer; it does not synthesize input.
- Lobby tile/view-state reconstruction is small at Battlegrounds lobby scale. No evidence currently justifies micro-optimizing cold overlay initialization.

The suite contains a several-thousand-mutation diagnostic, but there is no repeatable BenchmarkDotNet or ETW performance baseline. Performance claims should therefore remain qualitative.

## Known limitations

1. The live application composition pipeline is implemented but not validated against a real client. Direct, live, and replay paths share `TrackingSession`; only synthetic raw-line fixtures currently prove live semantics.
2. The manual overlay acceptance matrix has not been executed in this gate: start-before-Hearthstone, move, resize, minimize/restore, DPI changes, click-through, ALT interaction, pin/settings controls, and alt-tab focus behavior remain unverified on a real client.
3. The test corpus is primarily synthetic. There is no curated set of minimized real-match recordings covering patches, reconnects, spectator transitions, and abnormal termination.
4. The CI workflow is present locally but has not run on GitHub yet. Branch protection and required-check enforcement are not configured by this milestone.
5. There is no packaged installer, upgrade/rollback test, crash recovery test, telemetry, or long-duration soak test.
6. Card database/art assets, strategy analysis, and backend services are intentionally outside v0.1 and are not release blockers for the tracking core.

## Hearthstone edge cases not yet supported

- Power protocol support is intentionally limited to `GameEntity`, `PlayerEntity`, `TAG_CHANGE`, `FULL_ENTITY`, `SHOW_ENTITY`, `CHANGE_ENTITY`, `BLOCK_START`, and `BLOCK_END`. Other valid protocol records are ignored or represented as unknown.
- Block nesting recovery is bounded; highly corrupted streams can lose detailed parent context after the safety depth is exceeded.
- A same-path Power.log truncate-and-regrow that occurs entirely between observations and grows beyond the old byte offset can be indistinguishable from a normal append and may skip early replacement bytes.
- Log directory discovery checks configured roots and the supported session layout; unusual future Battle.net directory structures may require a compatibility update.
- Battlegrounds setup/combat compatibility tags are based on current HDT-observed behavior and can drift when Hearthstone changes undocumented tags.
- Phase detection and turn calculation cover the recorded v0.1 transition model, not every reconnect, spectating, tutorial, anomaly, or future Battlegrounds mode transition.
- Cross-match clearing is covered by synthetic raw-line integration tests, but truncated/restarted real-client logs remain unvalidated.
- Exact game type and authoritative local player identity are not present in the accepted Power.log subset. The conservative fallback uses only named BG-specific tags and the HDT-observed owner of `NEXT_OPPONENT_PLAYER_ID`; late attach can remain inactive if those signals are absent.
- A reconnect that emits `CREATE_GAME` rebuilds from subsequent/replayed events. Earlier lobby or board history cannot be reconstructed from a truncated stream.
- Unknown numeric GameTags remain representable for compatibility. Replay work is bounded, but semantic support for new tags requires an explicit compatibility update.

## Technical debt

- `RecordingSerializer` (~700 lines), `PowerLineParser` (~540 lines), `PowerLogTailer` (~400 lines), and the overlay code-behind are the largest maintenance units. They are cohesive enough for v0.1, but future changes should extract focused validators/codecs or view-state composition instead of extending monolithic methods.
- `PlayerTimeline` rebuilds/sorts immutable event collections on addition. The lobby scale is currently small, but there is no intrinsic live-match history cap because the live pipeline is not wired yet.
- `TrackingSession` owns EntityStore reset/lifecycle and supports a host-configurable entity bound; the default remains unbounded until real-client evidence establishes a safe live limit. Recording continues to enforce its stricter replay-specific limit.
- Application shutdown synchronously waits for background cleanup. Coordinator cancellation is covered and current continuations avoid the UI context, but a full WPF process shutdown timeout/failure-path test is still absent.
- The debug UI queue and native callback recovery are not directly covered by WPF/Win32 integration tests.
- No code-coverage threshold, fuzz/property test suite, or performance baseline is configured. The GitHub Actions gate still needs its first remote run and required-check branch protection.
- Process-name/window-class matching is pragmatic but not a strong identity model.

## Recommended v0.2 tasks

Priority order:

1. **P0 — Execute the real-client acceptance matrix.** Test lifecycle/reconnect evidence, launch ordering, move/resize/minimize/restore, mixed-DPI monitors, click-through, ALT interaction, focus/alt-tab, client restart, and Power.log rotation without modifying an active game unexpectedly.
2. **P1 — Enforce CI.** After the first successful remote run, make the Windows quality job a required branch-protection check for `main`.
3. **P1 — Build a minimized real-recording regression corpus.** Include reconnects, restart/rotation, empty boards, seven-minion boards, armor damage, deaths, nested blocks, malformed lines, and patch transitions.
4. **P1 — Add fuzzing and soak tests.** Target parser strings, replay JSON, extreme event streams, log rotation races, native window disappearance, and cancellation/shutdown.
5. **P1 — Refine live-state budgets and lifecycle signals.** Use real-client evidence to bound entity/tag/history cardinality and replace conservative mode detection if a supported stronger signal becomes available.
6. **P2 — Add performance baselines.** Measure tailer throughput/backpressure, parser events per second, several-thousand-entity mutation/snapshot work, replay stepping, and overlay update latency.
7. **P2 — Reduce maintenance hotspots.** Split the serializer/parser/UI code only along tested responsibility boundaries; avoid architecture churn before live integration evidence exists.

Production readiness should be reassessed only after the P0 items pass on a real Hearthstone client and in an automated regression environment.
